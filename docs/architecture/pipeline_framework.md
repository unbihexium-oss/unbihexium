## Abstract

This document specifies the processing pipeline framework of Unbihexium as implemented in [src/unbihexium/core/pipeline.py](../../src/unbihexium/core/pipeline.py), the task pipelines that wrap the model zoo task APIs, the `unbihexium pipeline` commands of the command line interface, and the tiling and mosaicking machinery that lets pipelines and models process rasters larger than one computation. It defines the contract of a pipeline step, the execution and error semantics of a run, what a run record and its provenance record contain, how random number generators are seeded, and exactly how tiles are placed and blended. It is written for users who compose their own processing chains, for contributors who add pipelines or change the tiling, and for reviewers who need to know what the run records do and do not prove. Every example in this document was executed against the current code.

## 1. Introduction

### 1.1 Scope

The framework has three layers:

1. **`core.pipeline`**: a generic, framework-neutral sequence of named steps with a run record and a provenance record ([Section 2](#2-pipelines), [Section 3](#3-run-records-reproducibility-and-provenance)).
2. **Task pipelines**: pipelines generated by `unbihexium.ai.base.register_task_pipeline` that run one model zoo task API on raster files, registered in `PipelineRegistry` ([Section 4](#4-task-pipelines)).
3. **The CLI**: `unbihexium pipeline list` and `unbihexium pipeline run` ([Section 5](#5-the-pipeline-commands)).

Tiling ([Section 6](#6-tiling-and-mosaicking)) is independent of the pipeline classes: it is used inside steps, inside the `Predictor` of `unbihexium.ai`, and directly by users.

### 1.2 Conventions

The key words MUST, MUST NOT, SHOULD and MAY in this document are to be interpreted as described in RFC 2119 [1] and RFC 8174 [2] when, and only when, they appear in all capitals. They state what a pipeline step or caller has to do for the framework to behave as described.

### 1.3 Status of the models

The task pipelines run model zoo models. The zoo has 520 models (130 families in four variants); apart from the 28 models of the 7 spectral index families, which compute exact formulas, they are untrained starter models with deterministic weights. A task pipeline run with a starter model completes and writes a valid file, but its content is not meaningful until the model is trained; pass a trained checkpoint as shown in [Section 5.3](#53-examples).

## 2. Pipelines

### 2.1 Configuration

`PipelineConfig` is a dataclass:

| Field | Default | Meaning |
| --- | --- | --- |
| `pipeline_id` | required | Identifier; an empty string raises `ValueError` |
| `name` | required | Human-readable name |
| `description` | `""` | Description |
| `version` | `"1.0.0"` | Version of the pipeline definition |
| `steps` | `[]` | Planned step names, for documentation; not used for execution |
| `parameters` | `{}` | Parameters of the steps; recorded in the run |
| `seed` | `None` | Seed of the random number generators; a negative seed raises `ValueError` |
| `deterministic` | `True` | Recorded in the configuration; it does not change execution |

The property `effective_seed` is `seed` if set, else the value of a `"seed"` entry in `parameters`, else `None`. `to_dict()` and `from_dict()` convert the configuration to and from a plain dictionary.

### 2.2 Steps

A step is a callable `Step = Callable[[dict[str, Any]], Mapping[str, Any]]`:

- A step MUST accept one dictionary of values and MUST return a mapping. Returning anything else fails the step with `TypeError`.
- The mapping returned by a step **replaces** the values: the next step receives `dict(output)`, not a merge of old and new values. A step that wants to pass values through MUST copy them into its output (for example `return {**values, "data": data}`).
- A step SHOULD NOT modify its input files; see [Section 3.3](#33-provenance) for why.

Steps are added with `add_step(step, name=None)`, which returns the pipeline so that calls can be chained, or with the decorator `@pipeline.step(name=None)`. The step name is the explicit name, else the function's `__name__`, else `step_<position>`. Names MUST be unique within a pipeline; a duplicate raises `ValueError`, and a non-callable step raises `TypeError`. `step_names` lists the names in order, and `len(pipeline)` is the number of steps.

### 2.3 Execution

`Pipeline.run(inputs=None, record_provenance=True)` executes the steps in order:

1. A `PipelineRun` is created in the state `pending`, with a snapshot of the configuration (including the executed step names) and the inputs converted to strings.
2. If the run has a seed, the generators are seeded ([Section 3.2](#32-seeding)).
3. The run moves to `running`. Each step gets a `StepRecord` with start and end time (ISO 8601, UTC), duration from `time.perf_counter()` and status; the duration is also stored as the metric `step.<name>.seconds`.
4. On success the final values are kept in `run.results` (the objects themselves) and in `run.outputs` (as strings), the run moves to `completed`, a provenance record is built, and the metric `run.seconds` is set.
5. If a step raises, its record gets the status `failed` and the error text `"<ExceptionType>: <message>"`, the run moves to `failed` with the same text in `run.error`, a provenance record of the inputs only is built, and **the exception is re-raised** to the caller.

There is no retry, no parallel execution of steps, no caching of intermediate results and no cancellation from inside a run; `PipelineRun.cancel(reason)` only sets the state of a record. `create_run(inputs)` creates a pending run without executing it. Every run of a pipeline object is appended to `pipeline.runs`.

### 2.4 States

`PipelineStatus` has the values `pending`, `running`, `completed`, `failed` and `cancelled`. `PipelineRun.start()` raises `RuntimeError` unless the run is `pending`.

## 3. Run records, reproducibility and provenance

### 3.1 The run record

`PipelineRun.to_dict()` and `to_json(path=None)` serialise a run with the keys `run_id` (a UUID 4), `pipeline_id`, `status`, `start_time`, `end_time`, `duration_seconds`, `config_snapshot`, `inputs`, `outputs`, `logs` (timestamped messages), `metrics`, `error`, `seed`, `steps` and `provenance`. `to_json(path)` creates the parent directory and writes the file. `results` is not serialised.

### 3.2 Seeding

When the effective seed is not `None`, `seed_everything(seed)` is called before the first step. It requires $0 \le \text{seed} < 2^{32}$ and seeds the Python `random` module, NumPy's legacy global generator (`np.random.seed`, used by the `np.random.*` functions) and, only if PyTorch has already been imported by the process, `torch.manual_seed`. Generators created by the steps themselves (for example `np.random.default_rng()` without a seed) are not affected; steps that need randomness SHOULD derive their generator from the configured seed.

### 3.3 Provenance

When `record_provenance` is true, the run gets a `ProvenanceRecord` ([src/unbihexium/core/evidence.py](../../src/unbihexium/core/evidence.py)) with:

- `inputs` and `outputs`: for every value that is a string or path naming an existing file, an `Evidence` record with the SHA-256 digest [4] of the file, its size, file name, role (`input` or `output`) and the key as description; every other value is recorded as the text `key=value`;
- `model_ids`: the value of the parameter `model_id` or `model`, if it is a string;
- `config`: the configuration snapshot;
- `environment`: Python version and implementation, `platform.platform()`, NumPy and Unbihexium versions, and the versions of SciPy, rasterio, PyTorch and ONNX Runtime if they are loaded;
- `digest`: the SHA-256 of the canonical JSON of the record, so that a later change of a stored record is detected by `ProvenanceRecord.from_dict(..., verify=True)`.

The record follows the entity-activity structure of W3C PROV-DM [5]: files are entities, the run is the activity.

Two properties follow from the implementation and matter when the record is used as evidence:

- Input digests are computed **when the run starts**, before the first step, and output digests when it ends. An input file that a step modifies is therefore recorded with the content that was read. A value of the input mapping that names a file that does not exist yet, such as an output path passed in the inputs, is recorded as text.
- The record proves which input bytes were present when the run started, which output bytes were present when it ended and which software versions were loaded. It does not prove that the recorded code produced the outputs.

### 3.4 Example

The script creates a synthetic scene, runs a three-step NDVI pipeline with a seed and writes the run record.

```python
import numpy as np
from rasterio.transform import from_origin

from unbihexium.core.pipeline import Pipeline, PipelineConfig
from unbihexium.indices import ndvi
from unbihexium.io import read_geotiff, write_geotiff

# A synthetic 4-band scene (blue, green, red, near infrared).
rng = np.random.default_rng(0)
stack = rng.uniform(0.02, 0.5, size=(4, 64, 64)).astype("float32")
write_geotiff(stack, "scene.tif", crs="EPSG:32635", transform=from_origin(500000, 6700000, 10, 10))

pipeline = Pipeline(PipelineConfig("ndvi", "NDVI of a scene", seed=0))


@pipeline.step()
def read(values):
    data, meta = read_geotiff(values["input"])
    return {**values, "data": data, "meta": meta}


@pipeline.step()
def compute(values):
    index = ndvi(nir=values["data"][3], red=values["data"][2]).astype("float32")
    return {"index": index, "meta": values["meta"], "output": values["output"]}


@pipeline.step()
def write(values):
    meta = values["meta"]
    path = write_geotiff(values["index"], values["output"], crs=meta["crs"], transform=meta["transform"])
    return {"output": path}


run = pipeline.run({"input": "scene.tif", "output": "ndvi.tif"})
print(run.status.value, pipeline.step_names, run.seed)
print(run.outputs)
evidence = run.provenance.outputs[0]
print(evidence.evidence_type.value, evidence.source, evidence.verify())
print([getattr(item, "source", item) for item in run.provenance.inputs])
run.to_json("runs/ndvi.json")
```

Output:

```text
completed ['read', 'compute', 'write'] 0
{'output': 'ndvi.tif'}
output ndvi.tif True
['scene.tif', 'output=ndvi.tif']
```

`runs/ndvi.json` then contains the metrics `step.read.seconds`, `step.compute.seconds`, `step.write.seconds` and `run.seconds`. The input mapping also names `ndvi.tif`, which does not exist when the run starts, so the provenance record lists it among the inputs as text and among the outputs with its digest, as explained in Section 3.3.

## 4. Task pipelines

### 4.1 Construction

`register_task_pipeline(pipeline_id, name, description, domains, factory, inputs=("input",), method="predict")` in [src/unbihexium/ai/base.py](../../src/unbihexium/ai/base.py) registers a factory `create(**kwargs)` in `PipelineRegistry`. Calling the factory:

1. creates `PipelineConfig(pipeline_id=pipeline_id, name=name, parameters=kwargs)`;
2. constructs the task API with `factory(**kwargs)`, so the keyword arguments are the constructor arguments of the task API (for example `variant`, `weights`, `threshold`, `tile_size`, `overlap`, `device`, `backend`);
3. adds one step, `run_task`, which reads every input key with `Raster.from_file`, calls the task method (`predict`, `predict_pair` or `enhance`) with the rasters, stores the result object as the attribute `pipeline.last_result`, and returns `{"result": result, <input keys>: <paths>}`.

The model is opened lazily on the first prediction. Catalogue models are built in memory with their starter weights; no file is written to the model store.

### 4.2 Registered task pipelines

| Pipeline | Task API | Default family | Method | Input keys | Output written by the CLI |
| --- | --- | --- | --- | --- | --- |
| `ship_detection` | `ShipDetector` | `ship_detector` | `predict` | `input` | GeoJSON FeatureCollection |
| `building_detection` | `BuildingDetector` | `building_detector` | `predict` | `input` | GeoJSON FeatureCollection |
| `water_detection` | `WaterDetector` | `water_surface_detector` | `predict` | `input` | Single-band GeoTIFF of class labels |
| `change_detection` | `ChangeDetector` | `change_detector` | `predict_pair` | `input1`, `input2` | Single-band GeoTIFF of class labels |
| `super_resolution` | `SuperResolution` | `super_resolution` | `enhance` | `input` | Multi-band float32 GeoTIFF |

The input bands must match the model: for example `ship_detector` expects red, green and blue, and `water_surface_detector` expects blue, green, red and near infrared. `unbihexium zoo info <model_id>` prints the expected channels.

## 5. The pipeline commands

### 5.1 `unbihexium pipeline list`

```text
Usage: unbihexium pipeline list [OPTIONS]

  List available pipelines.

Options:
  -d, --domain TEXT  Filter by domain.
  --help             Show this message and exit.
```

The command imports `unbihexium.ai`, so that the task pipelines are registered, and prints a table with the columns Pipeline ID, Name and Domains, sorted by identifier.

### 5.2 `unbihexium pipeline run`

```text
Usage: unbihexium pipeline run [OPTIONS] PIPELINE_ID

  Run a pipeline on raster files and write its result.

Options:
  -i, --input TEXT   Input file path.  [required]
  --input2 TEXT      Second input for two-date pipelines.
  -o, --output TEXT  Output file path.  [required]
  -p, --param TEXT   Pipeline parameter as KEY=VALUE.
  --help             Show this message and exit.
```

Behaviour, as implemented in [src/unbihexium/cli/main.py](../../src/unbihexium/cli/main.py):

- Each `-p KEY=VALUE` is split at the first `=`. The value is parsed as JSON when possible (`0.4` becomes a float, `true` a boolean) and kept as a string otherwise (`tiny`). The parameters are passed to the pipeline factory.
- The input mapping is `{"input": <-i>, "input1": <-i>}`, plus `"input2": <--input2>` when given.
- An unknown pipeline identifier prints `Error: pipeline not found: <id>` and exits with status 1. An exception raised by a step prints `Error: <message>` and exits with status 1.
- After a successful run, the result object stored in `last_result` is written to the output path with `unbihexium.ai.predict.write_result`, which chooses the format from the result type (table in Section 4.2) and creates the parent directory. The command prints `Completed: <run id> -> <output>`.
- The run record and its provenance are not written to disk by the command. Use the Python API ([Section 3.4](#34-example)) when a record is needed.

### 5.3 Examples

The inputs are two synthetic three-band GeoTIFFs created with:

```python
import numpy as np
from rasterio.transform import from_origin

from unbihexium.io import write_geotiff

rng = np.random.default_rng(0)
transform = from_origin(500000, 6700000, 1, 1)
for name in ("before.tif", "after.tif"):
    rgb = rng.uniform(0, 0.3, size=(3, 128, 128)).astype("float32")
    write_geotiff(rgb, name, crs="EPSG:32635", transform=transform)
```

Commands and their output (the run identifiers differ on every run):

```bash
unbihexium pipeline run ship_detection -i before.tif -o ships.geojson -p variant=tiny -p threshold=0.4
# Completed: b4625e1d-eefb-411c-9708-e5dd9812166b -> ships.geojson

unbihexium pipeline run change_detection -i before.tif --input2 after.tif -o change.tif -p variant=tiny
# Completed: dfd72665-5efc-4e98-b583-6c916853c603 -> change.tif
```

Invalid runs end with an error message and exit status 1:

<!-- doc-example: skip (shows the error messages of invalid runs) -->
```bash
unbihexium pipeline run water_detection -i before.tif -o water.tif -p variant=tiny
# Error: water_surface_detector_tiny expects 4 bands (blue, green, red, nir), got shape (3, 128, 128)

unbihexium pipeline run flood_mapping -i before.tif -o flood.tif
# Error: pipeline not found: flood_mapping
```

The first command wrote a GeoJSON FeatureCollection with `"model_id": "ship_detector_tiny"`, `"crs": "EPSG:32635"` and no features, and the second a single-band `uint8` GeoTIFF of 128 by 128 pixels in EPSG:32635. The empty detection result is expected: the starter model is untrained.

With a trained checkpoint (here from a short training run on synthetic data, which only checks the setup), the parameter `weights` selects the checkpoint:

```bash
unbihexium train ship_detector_tiny --synthetic 32 --epochs 2 --chip-size 64
unbihexium pipeline run ship_detection -i before.tif -o ships_trained.geojson \
    -p weights=runs/ship_detector_tiny/best.pt -p threshold=0.4
```

## 6. Tiling and mosaicking

### 6.1 Placement of tiles

All tiling functions of the library place tiles with the same rule. For an axis of length $L$, tile size $T$ and step $s$, the tile origins are

$$
\{0, s, 2s, \dots\} \cap [0, L - T] \;\cup\; \{L - T\},
$$

that is, tiles advance by $s$ and the last tile is shifted back so that it ends exactly at the raster edge. When $L \le T$ there is one tile at origin 0. Every tile therefore has the full size whenever the raster is at least one tile large, which keeps the input size of convolutional networks constant, and every pixel is covered. For example, $L = 300$, $T = 128$ and an overlap of 32 pixels ($s = 96$) give the origins 0, 96 and 172.

### 6.2 Implementations

| Module | Functions | Step | Blending |
| --- | --- | --- | --- |
| [core/tile.py](../../src/unbihexium/core/tile.py) | `tile_offsets`, `TileGrid`, `Tile`, `TileIndex`, `blend_weights`, `xyz_tile`, `xyz_bounds`, `xyz_bounds_mercator` | $T - \text{overlap}$ (pixels) | `last`, `average` or `linear` in `TileGrid.mosaic` |
| [utils/tiling.py](../../src/unbihexium/utils/tiling.py) | `tile_starts`, `tile_windows`, `tile_image`, `merge_tiles` | $T - \text{overlap}$ (pixels) | Weighted mean with optional per-pixel weights; uncovered pixels are NaN |
| [postprocessing/tiles.py](../../src/unbihexium/postprocessing/tiles.py) | `tile_positions`, `blend_weights`, `stitch_tiles` | $T - \text{overlap}$ (pixels) | `mean` or `linear` |
| [ai/inference.py](../../src/unbihexium/ai/inference.py) | `Predictor` (internal `tile_starts`, `blend_weights`) | Derived from an overlap fraction (Section 6.4) | Pyramid weights for dense outputs; margin rule and NMS for detections |

### 6.3 `TileGrid` and mosaicking

`TileGrid.for_shape(height, width, tile_size, overlap, crs, transform)` or `TileGrid.from_raster(raster, tile_size, overlap)` describes the grid; `tiles(raster)` yields `Tile` objects with the data (read with `Raster.read_window`), the pixel offset, the shape, and, when the raster has an affine transform, the transform and bounds of the tile. `Tile.with_data(array)` returns a tile with new data and the same placement, and `TileGrid.mosaic(tiles, dtype=None, nodata=0.0, blend="last")` puts processed tiles back together:

- `last` writes the tiles in order, so later tiles overwrite overlaps;
- `average` gives every tile equal weight;
- `linear` weights pixel $i$ of a tile of length $n$ along each axis by
  $$
  w(i) = \min\!\left(1,\; \frac{i + 0.5}{o},\; \frac{n - i - 0.5}{o}\right),
  $$
  where $o$ is the overlap, and multiplies the weights of the two axes. The result is $\sum w \cdot x / \sum w$, which equals the tile value wherever only one tile covers a pixel and feathers seams in the overlaps [6].

Non-finite tile values get weight zero, pixels covered by no tile get `nodata`, and integer output types are rounded. The example processes a two-band raster tile by tile and checks that the mosaic reproduces the untiled result:

```python
import numpy as np

from unbihexium.core import Raster, TileGrid

rng = np.random.default_rng(0)
raster = Raster.from_array(rng.random((2, 300, 500)).astype("float32"), crs="EPSG:32635",
                           transform=(10.0, 0.0, 500000.0, 0.0, -10.0, 6700000.0))

grid = TileGrid.from_raster(raster, tile_size=128, overlap=32)
print(grid.num_rows, grid.num_cols, grid.total_tiles)

# Process every tile (here: multiply by two) and put the results back together.
processed = [tile.with_data(tile.data * 2.0) for tile in grid.tiles(raster)]
mosaic = grid.mosaic(processed, blend="linear")
print(mosaic.shape, np.allclose(mosaic, raster.data * 2.0, atol=1e-5))

first = processed[0]
print(first.offset, first.shape, first.transform)
```

Output:

```text
3 5 15
(2, 300, 500) True
(0, 0) (2, 128, 128) (10.0, 0.0, 500000.0, 0.0, -10.0, 6700000.0)
```

### 6.4 Tiled model inference

The `Predictor` of `unbihexium.ai.inference` applies the tiling to model inference ([src/unbihexium/ai/inference.py](../../src/unbihexium/ai/inference.py)):

1. **Tile size.** The tile size is the `tile_size` argument or the variant's tile size (256 pixels for tiny and base, 512 for large and mega), rounded up to a multiple of $m = 2^{\text{depth}}$ of the variant (8 for tiny, 16 for base and large, 32 for mega), so that the encoder can halve it at every level.
2. **Step.** With the overlap fraction $f$ (default 0.25, clipped to $[0, 0.9]$), the step is $\max(m, \lfloor T (1 - f) \rfloor \text{ rounded down to a multiple of } m)$; for $T = 256$ and $f = 0.25$ it is 192 pixels.
3. **Normalisation and gaps.** The image is standardised with the per-band statistics stored in the model configuration by training (spectral index models are not normalised); non-finite values are set to zero for the network, and pixels where no band is finite are remembered as invalid.
4. **Padding.** Images smaller than a tile are padded by reflection (by edge replication for images one pixel wide or high) to the next multiple of $m$.
5. **Batches.** Tiles are stacked in batches of `batch_size` (default 4) and passed to the PyTorch or ONNX Runtime backend.
6. **Dense outputs** (segmentation, change detection, dense regression, spectral index, enhancement, super-resolution) are accumulated with pyramid weights $w_y(i) = \min(i + 1, h - i) / ((h + 1)/2)$, multiplied with the same function along $x$ and bounded below by $10^{-3}$; class logits are converted with a softmax before blending. The blended output is cropped to the image size (times the scale factor for super-resolution), and invalid pixels become NaN.
7. **Detections** are decoded per tile; a box whose centre lies within $T f / 2$ pixels of a tile edge that is not an image edge is dropped, the remaining boxes are shifted to image coordinates, boxes centred on invalid pixels are removed, and class-aware non-maximum suppression with an IoU threshold of 0.5 removes duplicates.
8. **Scene regression** models run once on the whole, padded image, without tiling.

Blending with overlapping tiles reduces the seams that appear at tile borders of convolutional predictions [3].

## 7. Limitations

- **No persisted run records from the CLI.** `unbihexium pipeline run` discards the run record and provenance (Section 5.2).
- **Sequential execution.** Steps and runs are executed sequentially in the calling thread; there is no scheduler, no distributed execution and no resumption of failed runs.
- **Several tiling implementations.** The modules in Section 6.2 implement the same placement rule independently and differ in their blending weights; results of the same data can therefore differ slightly in the overlaps depending on the function used.
