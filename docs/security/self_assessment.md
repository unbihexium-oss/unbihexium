## Abstract

This is the security self-assessment of Unbihexium, written by the maintainers along the outline of the self-assessment guide of the CNCF Technical Advisory Group for Security [1]. It summarises in one place what the software does, who and what it trusts, which security functions it provides, how it is developed and released, and how security problems are handled, and it points to the documents that describe each part in detail. It is written for users who decide whether to adopt the library, operators of the REST service, and reviewers who prepare a joint or external assessment. It is an internal analysis by the project: it is not an audit, not an independent assessment and not an attestation of the security of Unbihexium. No external security audit has been performed.

## 2. Overview

Unbihexium is a Python library for Earth observation, geospatial analysis, remote sensing and synthetic aperture radar, with a command line interface, an optional REST service and a model zoo of 520 locally built starter models.

### 2.1 Background

Earth observation software turns satellite, aerial and radar imagery into measurements such as vegetation indices, water extents, terrain derivatives or detected objects. Its inputs are large binary rasters (GeoTIFF, Zarr), vector documents (GeoJSON, GeoParquet), catalogue documents (STAC) that point to further files and URLs, and model files that contain learned weights or whole programs. These inputs often come from third parties: public archives, commercial providers, partners and users. The main security concerns of such a library are therefore the parsing of untrusted files, the loading of untrusted model files, requests to remote servers chosen by the user, and, when the analysis is offered as a network service, resource exhaustion and access control. Imagery can also show people and private property, so its processing can be subject to data protection law ([PRIVACY.md](../../PRIVACY.md)).

### 2.2 Actors

| Actor | Role | Isolation |
| --- | --- | --- |
| Library | Functions called by a Python program: input and output, indices, SAR, terrain, geostatistics, pipelines, inference | None of its own: it runs in the process of the caller, with the caller's privileges and file system access |
| Command line interface | The `unbihexium` command, a thin layer over the library | Runs as the invoking user; the CLI opens no network connection of its own |
| Model loaders and model store | Build, verify and load models; cache them under `UNBIHEXIUM_CACHE` | Digest verification for catalogue models; `torch.load(weights_only=True)` for checkpoints; ONNX graphs run in ONNX Runtime, not as Python code |
| REST service | `unbihexium serve`, a FastAPI application that runs predictions on submitted images | A separate process, normally in the non-root container image or the Kubernetes manifests with a read-only root file system; clients reach it only over HTTP |
| External parsers | GDAL (through rasterio), PROJ, GEOS, ONNX Runtime, PyTorch | Third-party code in the same process; outside the trust boundary of the project |
| Remote servers | STAC APIs, download URLs of registered checkpoints, remote rasters | Contacted only when the caller asks for it; certificate verification and timeouts apply |

The trust boundaries between these actors are drawn and explained in the [Security Model](../architecture/security_model.md), Section 2.

### 2.3 Actions

- **Reading a data file.** The caller passes a path. Rasters are parsed by GDAL; GeoJSON is parsed with the standard JSON parser and validated against RFC 7946 by `geojson_problems`; STAC items are validated by `STACItem.from_dict`. Invalid content raises `ValueError`. Nothing in a data file is executed.
- **Loading a catalogue model.** `load_model` checks that the identifier is known to the registry, builds or reads the starter weights and compares their SHA-256 digest with the packaged `digests.json`; a mismatch raises `VerificationError`.
- **Loading a checkpoint.** `load_checkpoint` reads the file with `torch.load(weights_only=True)`, checks the format marker and version, verifies the recorded weight digest and loads the state dictionary strictly.
- **Serving a prediction.** The service checks the API key (when configured) with a constant-time comparison, applies the rate limit (when configured), limits the request body to 10 MiB by default while it is received, decodes the image without unpickling, checks the pixel and value limits and the band count, resolves the model identifier against the registry only, runs the prediction in a thread pool and returns the result. Unexpected errors return the exception type only.
- **Searching a STAC API.** The client sends the request with certificate verification and a timeout, follows `next` links up to a page limit, and sends configured headers such as an `Authorization` token only to the origin of the API.

### 2.4 Goals

- Data files and documents are treated as untrusted: parsing them does not execute code, and malformed content raises `ValueError` rather than crashing the process.
- Catalogue models are exactly the models the catalogue defines: their weights are verified against published digests before use.
- Checkpoints are loaded without unpickling arbitrary Python objects.
- REST clients can select only registered models and bounded parameters, cannot name files, devices or backends, and cannot exceed the configured size limits; with an API key configured, every route except `/health` and the documentation routes requires it.
- The software sends no telemetry and contacts no server that the caller did not ask for.
- Released distributions and container images can be verified by users: checksums, Sigstore signatures, SLSA provenance and SBOMs ([SECURITY.md](../../SECURITY.md), Section 7).

### 2.5 Non-goals

- **Sandboxing the caller.** The library acts with the privileges of the calling process and does not confine paths chosen by its caller, including paths that STAC documents resolve to. Integrators who pass untrusted paths or catalogues must confine them themselves.
- **Vulnerabilities in GDAL, PROJ, GEOS, PyTorch or ONNX Runtime.** Malformed-raster and similar vulnerabilities in these libraries are reported upstream; the project responds by raising dependency bounds and rebuilding.
- **Safe execution of TorchScript or `torch.export` files.** These formats contain programs and must come from a trusted source.
- **Correct or safe predictions.** The starter models are untrained; a model that passes the integrity checks can still produce wrong or misleading results. Integrity establishes which weights are loaded, not whether they are good.
- **Transport security and user management in the REST service.** The service speaks plain HTTP and knows one shared API key; TLS, user accounts and fine-grained authorisation belong to the reverse proxy or platform in front of it.
- **Protection of the data processed.** The library neither encrypts nor anonymises imagery; data protection obligations stay with the deployer.

## 3. Self-assessment use

This self-assessment is created by the Unbihexium maintainers to perform an internal analysis of the security of the project. It is not intended to provide a security audit of Unbihexium, or to function as an independent assessment or attestation of the security health of Unbihexium.

It gives users of Unbihexium an initial understanding of its security, of where the security documentation is, of the security plans of the project, and of its security practices, both for the development of Unbihexium and for the security of Unbihexium itself. It is also the starting point for a joint assessment or an external audit, should the project seek one. The self-assessment is referenced as `security.assessments.self` in [security-insights.yml](../../security-insights.yml).

## 4. Security functions and features

### 4.1 Critical

These properties are part of the design, are not configurable, and are the primary items for threat modelling. A change to any of them requires an update of the [Security Model](../architecture/security_model.md).

| Component | Importance |
| --- | --- |
| No code from data | The package contains no `eval` or `exec`; YAML is read with `yaml.safe_load`; NumPy data from others is read with `allow_pickle=False` |
| GeoJSON and STAC validation | The two parsers of documents from other parties; bounded nesting depth; fuzzed with atheris on pull requests and weekly |
| Starter weight digests | `digests.json` fixes the weights of every catalogue model; `load_model`, `ensure_model` and `zoo verify` compare against it |
| Safe checkpoint loading | `torch.load(weights_only=True)`, format and version checks, digest check, strict state dictionary loading |
| Model identifier resolution | The REST service and the model store accept only identifiers known to the registry; identifiers with path separators or parent references are rejected |
| Streaming body limit | The request size middleware counts the bytes of bodies without `Content-Length`, so chunked uploads cannot bypass the limit |
| Credential scoping in the STAC client | Configured headers are sent only to the origin of the API |
| Error disclosure | Unexpected exceptions in the service become 500 responses with the exception type only |

### 4.2 Security relevant

These settings and components are configurable or deployment dependent and should be included in threat modelling of a deployment.

| Component | Default | Recommendation |
| --- | --- | --- |
| `UNBIHEXIUM_SERVING__API_KEY` | Unset: no authentication | Set it whenever the service is reachable beyond the local host |
| `UNBIHEXIUM_SERVING__RATE_LIMIT_PER_MINUTE` | 0: no rate limit | Set it, or limit at the reverse proxy, which also knows the real client address |
| `UNBIHEXIUM_SERVING__CORS_ORIGINS` | `*` | Restrict to the origins of the applications that call the service |
| `UNBIHEXIUM_SERVING__MAX_REQUEST_BYTES` and the pixel and value limits | 10 MiB; 2048 x 2048 pixels; 16 x 1024 x 1024 values | Lower them to what the application needs |
| TLS | None in the service | Terminate TLS at a reverse proxy or ingress |
| Container image and Kubernetes manifests | Non-root user, read-only root file system, dropped capabilities, no privilege escalation | Keep these settings; verify the image signature before deployment |
| Model sources | Catalogue models built locally | Load checkpoints and ONNX files only from trusted sources, TorchScript and `torch.export` files never from untrusted ones |

The requirements for deployers are listed in the [Security Model](../architecture/security_model.md), Section 10, and in [SECURITY.md](../../SECURITY.md), Section 8.

## 5. Project compliance

Unbihexium is not certified against, and does not claim conformance with, any security standard such as ISO/IEC 27001, SOC 2 or PCI DSS. The following frameworks are applied to the repository and its releases:

- **SLSA** [2]: distributions and container images carry signed build provenance from GitHub artifact attestations, produced by GitHub-hosted runners from a tagged commit ([Supply Chain Security](supply_chain_security.md), Section 6).
- **OpenSSF Scorecard** [3]: runs weekly and on changes to `main`; the result is published and shown in the README.
- **OpenSSF Security Insights** [4]: [security-insights.yml](../../security-insights.yml) describes the project, its contacts, its tools and its release artefacts.
- **REUSE** [5]: every file carries licence and copyright information, checked on every pull request.

How the project relates to the GDPR, the EU AI Act, the Cyber Resilience Act and export control law, and which obligations fall on deployers, is described in [COMPLIANCE.md](../../COMPLIANCE.md). That document is not legal advice.

## 6. Secure development practices

### 6.1 Development pipeline

- **Review.** [.github/CODEOWNERS](../../.github/CODEOWNERS) assigns every file to the maintainer. The branch protection rule of `main` requires the status checks listed in [ci_cd.md](../operations/ci_cd.md), Section 4.4, before a pull request is merged.
- **Contributions.** Contributors certify the Developer Certificate of Origin 1.1 in the pull request template; commits are not required to be signed. Pull request titles and commit messages follow Conventional Commits and are checked.
- **Tests.** The unit, integration and end-to-end tests run on CPython 3.10 to 3.14 on Linux and on 3.10 and 3.14 on macOS and Windows; line and branch coverage must stay at or above 85 %. The code examples of the documentation are run as well.
- **Static analysis.** ruff (including its security rules), pyright, Bandit and CodeQL (`security-extended`, Python and GitHub Actions).
- **Dependencies.** Runtime and development dependencies are locked with SHA-256 hashes and installed with `--require-hashes` in CI and in the container image; pip-audit and the GitHub dependency review fail on known vulnerabilities; Dependabot proposes version and security updates; the licences of all dependencies are checked.
- **Workflows.** Every action is pinned to a full commit SHA, every workflow starts with a read-only token and grants write permissions per job, and TruffleHog scans for secrets.
- **Fuzzing.** atheris targets for the GeoJSON and STAC parsers run on pull requests that touch them and weekly; crashing inputs become regression files that the ordinary test suite replays.
- **Releases.** Releases are built from a tag on GitHub-hosted runners, signed with Sigstore, attested with SLSA provenance and an SPDX SBOM, and uploaded to PyPI through trusted publishing with PEP 740 attestations, so no upload credential is stored. Container images are pinned by base image digest, scanned with Grype, signed with cosign in keyless mode and attested.

The controls are described with their configuration and known gaps in [Supply Chain Security](supply_chain_security.md).

### 6.2 Communication channels

- **Internal.** The project has one maintainer. Decisions are recorded in pull requests, issues and the documents under version control, as described in [GOVERNANCE.md](../../GOVERNANCE.md).
- **Inbound.** Questions and ideas go to GitHub Discussions, defects and requests to the issue forms ([SUPPORT.md](../../SUPPORT.md)); vulnerabilities go privately to GitHub private vulnerability reporting or by e-mail ([SECURITY.md](../../SECURITY.md), Section 3).
- **Outbound.** Releases are announced as GitHub releases with release notes and recorded in [CHANGELOG.md](../../CHANGELOG.md); vulnerabilities are published as GitHub security advisories of the repository. There is no mailing list.

### 6.3 Ecosystem

Unbihexium sits on top of the scientific Python and open geospatial stack: NumPy and SciPy for arrays, rasterio and GDAL for rasters, pyproj and PROJ for coordinate reference systems, Shapely and GEOS for geometries, and PyTorch and ONNX Runtime for models. It exchanges data in open formats (GeoTIFF, Cloud Optimized GeoTIFF, Zarr, GeoParquet, GeoJSON, STAC), so its outputs can be used by other tools and it can process the outputs of other tools. Its security therefore depends substantially on those libraries, and a vulnerability in one of them usually affects Unbihexium users through the dependency, not through Unbihexium code.

## 7. Security issue resolution

### 7.1 Responsible disclosure process

Vulnerabilities are reported privately through GitHub private vulnerability reporting (preferred) or by e-mail to the maintainer. Reports must not be filed as public issues, discussions or pull requests. The full process is in [SECURITY.md](../../SECURITY.md), Sections 3 to 5.

### 7.2 Vulnerability response process

The sole maintainer receives and handles every report; there is no security team, on-call rotation or bug bounty. The maintainer acknowledges receipt, assesses scope and severity with CVSS 4.0, develops the fix in the private fork of the advisory with the reporter invited to review it, adds regression tests, releases a patch version of the latest release series and publishes the advisory with the affected and fixed versions, the severity, the credit and a CVE identifier requested from GitHub. The best-effort targets are:

| Step | Target |
| --- | --- |
| Acknowledgement of receipt | within 7 calendar days |
| Initial assessment | within 21 calendar days |
| Fix for critical and high severity | within 30 days of confirmation |
| Fix for medium and low severity | within 90 days of confirmation, or with the next regular release |
| Public disclosure | with the fix, and no later than 90 days after the report unless both parties agree otherwise |

### 7.3 Incident response

A vulnerability in a dependency is handled as described in [Vulnerability Management](vulnerability_management.md), Section 7: the affected lower bound is raised, the lock files are regenerated and a patch release is made where the vulnerable code is reachable through Unbihexium. A suspected compromise of a credential or of a published artefact is handled as described in [Secrets and Tokens](secrets_and_tokens.md) and [Releasing](../operations/releasing.md): the credential or trusted publisher is revoked first, an affected release is yanked on PyPI and replaced by a new patch version, and the incident is published as an advisory. Because releases carry signatures and provenance, users can check whether an artefact was built by the release workflow from a tag of this repository.

## 8. Appendix

### 8.1 Known issues over time

No security advisory has been published for Unbihexium. The review for the [Security Model](../architecture/security_model.md) found five weaknesses on the main branch before any of them was released: path traversal in `zoo clear`, unbounded recursion in the GeoJSON validator, STAC credentials sent to other hosts, an unbounded rate limiter table and an incomplete `zoo verify`. All five are fixed, covered by unit tests and listed in [CHANGELOG.md](../../CHANGELOG.md), Section 4.5. The releases 1.0.0 and 1.0.1 predate the current release pipeline and carry no signatures or provenance ([Supply Chain Security](supply_chain_security.md), Section 10).

### 8.2 OpenSSF Best Practices

The project has not yet applied for the OpenSSF Best Practices badge [6]. Most criteria of the passing level are met by the documents and workflows above: a public repository and issue tracker, a licence, contribution and security policies, a changelog, automated tests with coverage requirements, static analysis, dynamic analysis through fuzzing, signed releases and vulnerability response targets. Criteria that would need attention are the bus factor of one maintainer, which the [roadmap](../../ROADMAP.md) addresses, and a documented response record, which does not yet exist because no vulnerability has been reported.

### 8.3 Case studies

- **Batch analysis of public imagery.** A researcher computes vegetation and water indices over a Sentinel-2 time series read from a STAC API. Relevant controls: validation of the STAC items, credential scoping in the STAC client, no telemetry. The researcher reviews asset hrefs of catalogues from unknown sources before loading them.
- **Prediction service in a cluster.** An organisation deploys the REST service from the signed container image with the Helm chart behind an ingress that terminates TLS. Relevant controls: API key, rate limit, request size and image limits, model identifier resolution, non-root and read-only container. The operator verifies the image signature and restricts CORS.
- **Training on own data.** A user fine-tunes a catalogue model on labelled imagery and distributes the checkpoint to colleagues. Relevant controls: checkpoints loaded with `weights_only=True` and verified against their recorded digest. The colleagues obtain the checkpoint over a trusted channel, since a digest in the file itself does not prove who wrote it.

### 8.4 Related projects

Users often compare Unbihexium with general geospatial libraries such as rasterio, GeoPandas and xarray, and with Earth observation machine learning frameworks such as TorchGeo. The first group provides the input and output layers that Unbihexium builds on and has a similar attack surface for file parsing. Compared with the second group, Unbihexium adds a REST service, which widens the attack surface to network clients, and a model catalogue with digest-verified starter weights, which narrows the risk of loading substituted catalogue models.
